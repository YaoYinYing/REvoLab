# Scientific Graph

> **Status:** Accepted. Defines the logical graph semantics: which node categories
> exist, which edges are valid, whether edges are immutable, and how semantic
> mistakes are prevented. Deliberately relational (ADR-0003) — **no graph DB**, no
> RDF, no graph infrastructure.

REvoLab is, at its heart, one logical directed graph over durable node categories,
assembled at the application layer over relational tables.

## Node categories

Very few — anything more is premature ontology, not required:

| Node | Kind | Durable record |
|---|---|---|
| Project | container/scope | `projects` |
| ScientificObject | scientific entity | `scientific_objects` + per-type tables |
| RunReference | external execution identity card | `run_references` |
| SessionReference | external interactive-session identity card | `session_references` |
| ArtifactReference | external output identity card | `artifact_references` |
| LiteratureReference | external publication citation | `literature_references` |
| ExternalReference | external lookup/cache identity handle | `external_references` |
| Evidence | interpreted claim | `evidence` |
| Decision | committed conclusion | `decisions` |

The references, Evidence, and Decision **are** themselves graph nodes — they are
not flattened into relation payloads. This keeps provenance reconstructable.
`SessionReference` covers REvoDesign's interactive handoff; `ExternalReference`
covers OpenBio lookups/cache. All are neutral identity cards; none copies external
execution truth.

## Edges (typed, directed, with optional rationale/payload)

**This is the single canonical definition of the `relation_type` closed enum.** No
other document lists a competing scientific-relation vocabulary; `RelationType` lives
in Core (one closed enum, generated into the API contract and Agent tool schemas) and
is not extensible by a runtime plugin.

```text
ScientificObject --derived_from-->  ScientificObject   (project-internal lineage)
ScientificObject --variant_of-->    ScientificObject   (a variant of a parent entity)
ScientificObject --represents-->    ScientificObject   (a structure/artifact represents a variant/protein)
ScientificObject --generated_by-->  RunReference       (an output object was generated by a run)
ScientificObject --evaluates-->     ScientificObject   (an assay/run evaluates a variant)
Decision         --selects-->       ScientificObject   (a decision selects a variant/construct)
ScientificObject --consumed_as_input_by--> RunReference
RunReference     --produced-->      ArtifactReference  (single owning produced edge)
ArtifactReference--imported_as-->   ScientificObject   (origin of a derived object)
Evidence         --supports-->      ScientificObject | Evidence
Evidence         --contradicts-->   ScientificObject | Evidence
Decision         --cites-->         Evidence           (DecisionEvidence join, + cited_as polarity)
Decision         --supersedes-->    Decision
```

Node-target types: `ScientificObject`, `RunReference`, `SessionReference`,
`ArtifactReference`, `LiteratureReference`, `Evidence`, `Decision`.
(`LiteratureReference`==`cited_by` edges are recorded through Evidence, not a direct
edge, to keep the claim model.)

- `consumed_as_input_by`/`produced`/`imported_as` apply to both `RunReference`
  (REvoCompute) and `SessionReference` (REvoDesign) nodes: an object is consumed as
  input by a run or an interactive session, which produces an artifact that may be
  imported as a derived object.
- `supports`/`contradicts` may target another Evidence (evidence-to-evidence
  scholarly disagreement is real and cheap to record).
- `cites` goes through the existing `decision_evidence` join, extended with a
  per-citation `cited_as` polarity (supports/contradicts/context) so a Decision can
  honestly record that it was made *despite* contradicting evidence.
- `generated_by`, `evaluates`, `selects` are **kept** — they were required by the
  design brief (TODO Layer 4) and are jointly necessary to express
  `Artifact --generated_by--> Run --evaluates--> Variant` and
  `Decision --selects--> Variant`.

## One generic Relation vs several domain tables

**Decision: one generic Relation model** (typed `source/target/relation_type/
payload/rationale`), not several per-type edge tables — *for now*.

Rationale:
- The edge vocabulary is small and stable; per-type tables would multiply
  migrations without a demonstrated need.
- Payload/rationale is optional on every edge; a single table carries it uniformly.

**Target typing:** because edges can target Evidence and Decision (not only
ScientificObject), the `relations` table must support a **polymorphic target**. The
concrete form is a nullable discriminator — `source_node_type` / `target_node_type`
plus separate nullable FK columns for each node kind (or a small polymorphic-association
scheme) — so `supports/contradicts → Evidence` and `supersedes → Decision` are
representable without weakening referential integrity. `source` is always a
ScientificObject, RunReference, Evidence, or Decision per the edge table above; the
target type varies by edge. The payload (`rationale`) is frozen at write time on
immutable edges.

**When to split:** if a specific edge accumulates a rich, frequently-queried schema
of its own (e.g. a `cites` edge needing per-citation confidence), promote **that**
edge to a dedicated join table. `DecisionEvidence` is already promoted because it
is heavily queried. This is a "wait for the second real use case" rule, not
speculative generalization.

## Which edges need payload/rationale/provenance

- All edges carry an optional `rationale` (why the edge exists).
- Edges that represent a historical fact (`produced`, `imported_as`,
  `consumed_as_input_by`, `supersedes`, committed `cites`) are **immutable**
  provenance edges — their payload/rationale is frozen at write time.
- Edges that represent live interpretation (`supports`/`contradicts`, `derived_from`
  between objects) are append-only: a correction adds a *new* edge or marks a
  superseded one, it never rewrites the old one.

## Are edges immutable?

**Yes, once written.** A Relation is a provenance node: it is created with its
rationale and, once it influences later work or is a historical fact, it is never
updated or deleted. A wrong edge is corrected by adding a **superseding edge** or
marking it superseded — never by mutating it. (This is a deliberate divergence from
the bootstrap, whose Relation has no immutability rule.)

## How relation types are extended

The set of valid `relation_type` values is the **Core-owned closed enum defined in
the Edges section above** (the canonical `RelationType`; it supersedes the bootstrap
`RelationPolarity` enum). Adding a new scientific relation is a deliberate, reviewed
Core change — it is Core's scientific-semantics vocabulary and is not extensible by a
runtime plugin. (This mirrors the object-type registry philosophy: schema decisions
are durable.) The frontend, Agent tool schemas, and skills all derive from this single
enum via the generated contract — it is never duplicated by hand.

## Preventing invalid semantic combinations

- **Schema/validation layer:** relation must connect two distinct objects; both
  endpoints must belong to the project (already enforced); the `relation_type`
  must be a known value; self-relations rejected.
- **Domain-service layer:** higher-level semantic rules (e.g. "a Decision cites only
  Evidence in the same project", "an ArtifactReference has exactly one owning
  `produced` edge") live in the domain service, not in the schema.
- Rule of thumb: put **structural** invariants (distinctness, membership, known
  enum) in schema validation; put **semantic** invariants (what may relate to what,
  single-owner edges) in the domain service.

## What the graph must answer

A minimal provenance graph able to reconstruct (see `EVIDENCE_PROVENANCE.md`):

```text
Why does this scientific object exist?        → derived_from / imported_as / consumed_as_input_by chains + citing Decisions
Where did this structure come from?           → Structure -imported_as-> ArtifactReference -produced-> RunReference -consumed_as_input_by-> inputs
Which run created this artifact?              → ArtifactReference -produced-> RunReference (single owning edge)
Which evidence caused which decision?         → Decision -cites-> Evidence -supports/contradicts-> target
```

Recorded in **ADR-0010**.
